# C6 版本历史膨胀率测量（先量后改）

> 路线图 C6 给了两条路：写 `pruneHistory()` 真删旧提交，还是只做 `git gc`、提交不删。
> 选哪条取决于**真实膨胀率**，而"git 会增量压缩、所以膨胀很小"只是一句直觉。
> 直觉要先变成数字，否则要么白写一个会删数据的危险功能，要么在一个真会膨胀的场景里偷懒。
> 这份文档就是那个数字。

## 环境口径

| 项 | 值 |
|---|---|
| 构建 | Debug（本机验证构建；`commitSnapshot` 的耗时绝对值不代表 Release，**膨胀率与 gc 是结构性的，与构建类型无关**） |
| Qt | 6.5.3 |
| git | 系统 git（PortableGit） |
| 样本 | 400 行带标题/列表的 Markdown 笔记，首版约 16.8 KB |
| 档位 | quick（60 次提交；全量是 300 次，结论不依赖这个量级） |

## 主结果（60 次保存）

| 指标 | 追加型（文档越来越长） | 改写型（长度基本不变） |
|---|---|---|
| 文档大小 | 16.8 KB → 24.4 KB | 16.8 KB → 19.9 KB |
| `.git` 占用（60 版） | **176 KB** | **166 KB** |
| 每版平均增量 | **2.93 KB** | **2.77 KB** |
| 若每版存完整副本 | 1236 KB | 1099 KB |
| `git gc` 后 | 77.5 KB（收回 56.0%） | 77.2 KB（收回 53.5%） |
| gc 后版本可读性 | 60 / 60 全可读 | 60 / 60 全可读 |
| 单次 `commitSnapshot` | 中位 1881 ms | 中位 1854 ms |
| 单次 `git gc` | 2107 ms | 2343 ms |

## 判读

1. **膨胀率远低于预期，`pruneHistory()` 不需要做。**
   60 次保存、文档从 16.8 KB 长到 24.4 KB，`.git` 只有 176 KB —— **每版平均 2.93 KB**。
   按这个速度，即使保存 1000 次（真实使用里已经是几年的量），也就 ~3 MB。
   路线图 C6 里"膨胀远小于预期"那句直觉，被数字证实了：git 的 delta 压缩对
   "快照只有一个文件、每版只差几行"这种模式是近乎免费的。

2. **真正该做的是 `git gc`，而且它已经证明安全。**
   一次 gc 能收回约 55%，且 **gc 之后 60 个版本一个不少、全部可读**（`contentOf` 逐个验证过）。
   这是路线图 C6 Step 2 要求的"prune 不破坏剩余版本可读性"的直接证据 ——
   只不过对象从 prune 换成了 gc（gc 更安全：它只重打包，不删提交）。

3. **但 `gc` 不能每次保存都跑。** 单次 gc 耗时 2.1~2.3 秒，而一次 commitSnapshot 才 1.9 秒。
   每次保存都 gc 等于把保存成本翻倍。正确做法是**按计数节流**：攒够一批（比如 20 次）才 gc 一次，
   这正好落在路线图 C6 说的"每 20 次提交检查一次，不要每次都 gc"上。

4. **单次提交 1.9 秒，这是另一个独立的问题（不在 C6 范围内）。**
   commitSnapshot 每保存一次要起一个 git 进程（`add` + `commit` 两次 QProcess 往返）。
   1.9 秒对"Ctrl+S 之后等多久"来说偏长，但这属于**保存路径的交互延迟**，
   和"历史仓库会不会膨胀"是两件事。C6 只回答后者：**不会膨胀，所以不需要 prune**。
   保存延迟若要优化，方向是减少进程往返或把快照写入挪到后台（和 A1 索引同一个思路），
   那是另一个任务，不在这里顺手做。

## 结论（对应路线图 C6）

- ❌ 不实现 `pruneHistory()`：膨胀率（每版 2.93 KB）证明它是个没有现实收益、却有删数据风险的功能。
- ✅ 采用路线图 C6 的"更简单稳妥的替代"：只做 `git gc`，提交不删。
- ✅ `gc` 按计数节流触发（攒够一批再跑），不每次保存都跑。
- ✅ 已测：gc 之后所有版本仍可读（数据安全是硬前提，不是优化项）。

> 实现落点：`VersionControl` 无需新增 prune 接口；`gc` 的触发策略属于调用方
> （保存流程）的事，本测量只提供"该不该 gc、多久 gc 一次"的依据。
